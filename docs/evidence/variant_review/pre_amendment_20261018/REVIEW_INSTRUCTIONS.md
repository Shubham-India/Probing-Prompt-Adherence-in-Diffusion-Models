# Variant and lexicon review (H3) — instructions

**Purpose.** Human check that every benchmark prompt says exactly what its constraints say, that every variant makes only its intended change, and that the lexicon is usable. It is the evidence for the owner gate `variant_review_complete` (needed by DEV_CORE and all TEST stages). The gate stays `false` until you set it yourself after step 6.
**Scope.** All 1,674 prompts (main benchmark 1,410 + PS size family 264; DEV and TEST) and 73 lexicon entries. Reading TEST *prompt text* is part of the benchmark design and does not unseal TEST: no TEST image exists or is generated by this review.
**Not evidence of anything experimental.** The Kaggle PREFLIGHT for commit `d06a1d5` is infrastructure evidence only (environment, identities, timings).

## Files
| File | What it is |
|---|---|
| `variant_review.csv` | one row per prompt: DEV first, each scene's canonical prompt (CAN) followed by its variants |
| `lexicon_review.csv` | nouns and plurals, colours, colour/noun synonyms, relation phrases, confusable pairs |
| `review_inputs.json` | SHA-256 of the benchmark files these sheets were built from, row counts, flag counts |
| `variant_review_evidence.json` | written by the checker (step 5); not present until then |
Built by `python scripts/build_variant_review.py`; checked by `python scripts/check_variant_review.py`.

## Columns
Read-only: `item_id, split, source, scene_id, category, variant, canonical_prompt, prompt, intended_change, constraints, auto_flags` (`used_in_prompts` in the lexicon sheet). **Fill only:** `decision`, `reason`, `reviewer`, `review_date` (YYYY-MM-DD). Editing any other cell makes the checker refuse the review.
`decision` is one of:
- **PASS**: the prompt is grammatical, natural enough for an image prompt, expresses every listed constraint and nothing else, and (for a variant) makes only the change in `intended_change`.
- **FAIL**: invalid as specified (wrong or missing constraint in the text, a second change, ungrammatical or misleading wording, a variant that no longer matches its definition). `reason` required.
- **AMBIGUOUS**: you cannot decide alone (e.g. a synonym that may change the colour). `reason` required. The checker will not accept a finished review while any AMBIGUOUS remains; resolve each one to PASS or FAIL (keep the reason).
A **PASS on a row with `auto_flags`** needs a short `reason` saying why the flag does not invalidate it.

## What to check per variant
| Variant | Intended change (definition) | Typical failure |
|---|---|---|
| CAN | reference | constraint not expressed, extra attribute, odd wording |
| PAR | synonyms from the lexicon only; constraints identical | synonym changes the meaning (hue, material, noun reading) |
| ORD | mention order swapped (converse relation where needed); constraints identical | relation direction changed by the rewrite |
| CF-C | colour assignment changed (swap) | other field also changed |
| CF-A | one colour inserted or removed | more than one attribute changed |
| CF-R | spatial relation reversed | objects or colours also changed |
| CF-N | requested count changed | object or colour changed |
| CF-O | one object deleted or inserted with its constraints | remaining prompt ambiguous or unnatural |
| CF-S (PS family) | relative size swapped | colour or relation changed |
Lexicon: PASS a noun if a detector query of that word is a reasonable target and the plural is right; PASS a synonym only if it names the same colour/object in an image prompt; PASS a confusable pair entry if keeping such pairs out of the same scene is right.

## Automatic flags (pre-checks, nothing was corrected)
The builder checks text against constraints (nouns, colour-noun adjacency, counts, relation direction, size words, stray colour/number/relation words), the change against the variant definition, grammar (a/an, number agreement), duplicates and confusable pairs. Checks for text, change, grammar and confusable pairs found **no** problem in the current benchmark; they were confirmed to fire on deliberately broken prompts (`tests/test_variant_review.py`). Flags that remain and need your judgement:
| Flag | Rows | What to decide |
|---|---|---|
| `SYNONYM-CHECK` | 205 PAR rows | whether *golden, ivory, ebony, violet, emerald, tangerine, azure* still mean yellow, white, black, purple, green, orange, blue in an image prompt (decide once in `lexicon_review.csv`, then apply consistently to the PAR rows) |
| `DUPLICATE-CROSS-SPLIT` | 20 CF-O rows | single-object CF-O prompts such as "a shoe on a wooden table" occur in both DEV and TEST; decide whether identical prompt text across splits is acceptable for these counterfactuals |
| `DUPLICATE` | 53 rows (CF-O, CF-A, 3 CAN, 1 ORD) | identical text within a split, from different scenes (e.g. main `sg_0091_CAN` = PS `psD05_P_CAN`) |
| `METADATA` | all 90 CF-O rows | `n_objects` is not updated after the deletion; the R3 analysis does not use this field (decide whether it matters; do not edit the sheet) |

## Candidate decisions (to save you work)
`candidate_review.csv` proposes a decision, reason, evidence, confidence and the rule for every row (`python scripts/propose_variant_review.py`; summary and groups in `candidate_summary.json`). They are proposals, not your decisions; they never touch the sheets. Two research-design choices are in `OWNER_DECISIONS.md` (Q1 lexicon amendment, Q2 duplicates). After answering them, adopt the candidates you agree with in one command (your name and date are recorded; existing decisions are never overwritten; candidates that depend on an unanswered question are skipped; `--exclude ITEM_ID ...` to decide some rows yourself, `--only-rules` to adopt group by group):
`python scripts/adopt_candidate_review.py --reviewer "<your name>" --date YYYY-MM-DD --answers Q1=A,Q2=A`
Spot-check at least a few rows of every group in `candidate_summary.json` before adopting it.

## Steps
1. Open `variant_review.csv` and `lexicon_review.csv` in LibreOffice Calc or Excel (import as UTF-8, comma-separated). Do the lexicon sheet first: it settles the 205 synonym flags.
2. Fill `decision`, `reason`, `reviewer`, `review_date` for every row. Filter on `auto_flags` to see flagged rows; read every row, not only flagged ones.
3. Save in place as **CSV UTF-8** (Excel: "CSV UTF-8 (Comma delimited)"), keeping the column order and header. If the checker later says columns were edited, the spreadsheet changed a cell on saving; fix that cell back.
4. You may save part-way and continue later; the builder never overwrites a sheet that exists.
5. Run `python scripts/check_variant_review.py`. It writes `variant_review_evidence.json` and exits 0 only when the review is complete, no AMBIGUOUS remains, no lexicon entry FAILs, and fewer than 20% of prompt rows FAIL (H3).
6. Act on the result:
   - **FAIL items present (even below 20%)**: they must be fixed or removed before generation. That is a benchmark amendment, the owner's decision: record it in `docs/R3_DECISION_LOG.md` (date, items, reason), change the benchmark generator/data, re-run `python src/benchmark_v2.py --validate` and `--validate-ps`, rebuild the sheets with `python scripts/build_variant_review.py --out docs/evidence/variant_review_r2 --carry-over docs/evidence/variant_review` (unchanged items keep your decisions), review the changed rows, and check again on the new folder.
   - **20% or more FAIL**: H3 fails; stop and redesign the affected variant types before any generation.
   - **`criteria_met: true` and no FAIL left**: commit the completed sheets and evidence (`docs/evidence/variant_review/`). Then, and only then, set `"variant_review_complete": true` in `configs/stage_gates.json` yourself, commit, rebuild the release (`python scripts/build_release.py`, require `dirty=False`) and upload the new `gbc-source` version before DEV_CORE.
The checker and builder never change `configs/stage_gates.json`, the benchmark, or the protocol.
